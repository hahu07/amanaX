# Milestone 7 — Profit Distribution

Status: **gate met.** A Custodian can calculate a profit distribution for an issued note, pro-rated exactly across every investor's holding; a Trustee approves it as oversight; and each investor's own statement is recorded as its own, privacy-isolated on-ledger record — verified live in a browser across three role logins (Custodian, Trustee, Investor), with the privacy isolation additionally proven at the Daml Script level via a direct `queryContractId` negative assertion.

## What was built

### DAML (`daml/main/daml/AmanaX/Distribution/Distribution.daml`, new)
- `DistributionShare` — a plain data record (`investor`, `units`, `amountNGN`), computed off-ledger by the backend from the note's live `Allocation` holdings at proposal time, the same "backend computes, ledger records" pattern already used for `RegulatorySubmission`'s `documents` field (Milestone 4).
- `DistributionRequest` (signatory custodian, observer trustee/issuingHouse/sponsor) → `_Withdraw` (custodian) / `_Reject` (trustee) / `_Approve` (trustee, **returns `[ContractId ProfitDistribution]`** — a list, not a single contract).
- `ProfitDistribution` (signatory custodian **and** trustee, observer **just that one investor** + issuingHouse + sponsor) — one instance created **per investor share**, not one contract holding the whole cap table. `DistributionRequest_Approve`'s body is `forA shares $ \s -> create ProfitDistribution with ...`, using `forA` over the list — both custodian's (the request's signatory) and trustee's (the choice's controller) authority are available for creating every one of the N contracts in that single transaction.
- `daml/test/daml/AmanaX/Distribution/DistributionWorkflowTest.daml` — `distributionApprovalTest` (two investors, 10 and 5 units of the same note, ₦1,500,000 distributed → exactly ₦1,000,000 / ₦500,000; asserts `length distributionCids === 2`; asserts investor B's `queryContractId` for investor A's distribution contract returns `None` — the literal Daml-level proof of privacy isolation; asserts `query @ProfitDistribution investorA` returns exactly one record, not two) and `withdrawAndRejectDistributionTest`.

### Backend
- **`ledger/commands.ts`** gained `submitExerciseMulti` — the existing `submitExercise` only returns the *last* `CreatedEvent` in a transaction, which would silently drop every `ProfitDistribution` but one; this new helper returns every `CreatedEvent`, needed because `DistributionRequest_Approve` creates N contracts in a single transaction.
- **`ledger/subscriptions.ts`** gained `listAllocationsForInstrument` (the full list, not just the sum `sumAllocatedNGN` already computed — needed to build each investor's pro-rata share, not just check a total).
- **`ledger/distributions.ts`** (new) — `createDistributionRequest`, `listDistributionRequests`, `findDistributionRequestById`, `approveDistributionRequest` (uses `submitExerciseMulti`), `rejectDistributionRequest`, `withdrawDistributionRequest`, `listProfitDistributions`.
- **`api/distributions.ts`** (new) — `POST /investment-notes/:id/distributions` (Custodian; body `{periodLabel, totalAmountNGN}` — everything else, including the pro-rata shares themselves, is server-computed from the note's live `Allocation`s, never client-supplied), `GET /distribution-requests`, `/approve`, `/reject`, `/withdraw` (Trustee/Custodian as appropriate), `GET /profit-distributions` (any legitimate role; an Investor's own query is naturally scoped to their own records by Daml's per-investor observer design — no special-casing needed in the route, unlike `GET /investment-notes`).
- **`api/issuance.ts`**'s `NOTE_READERS`/`readerParty` extended to include `Custodian`, routed through the Platform Operator's party (same reasoning as `Investor` in Milestone 6 — a Custodian has no stakeholder relationship to a note until it proposes a distribution for it).
- **Pro-rata computation with an exact-sum guarantee** (`api/distributions.ts`'s `computeShares`): each share is `totalAmountNGN * (investorUnits / totalUnits)`, rounded to 2dp; the *last* share absorbs whatever rounding remainder is left, so the shares always sum to exactly `totalAmountNGN` rather than being a cent or two off — verified directly by a backend test asserting `shares.reduce(...) === totalAmountNGN`.

### Frontend
- **`lib/format.ts`**'s `formatNGN` — see Findings #2.
- **`api/distributionsApi.ts`**, **`hooks/useDistributionRequests.ts`**, **`hooks/useProfitDistributions.ts`** (new) — the established typed-client / fetch-hook pattern.
- **`dashboards/custodian/CustodianDashboard.tsx`** (rewritten from `RolePlaceholder`) — browses issued notes (via the Operator's party, same as Investor), a "Propose distribution" action opening a period/amount form, "Pending requests" (with withdraw), "Distribution history" (every per-investor record the Custodian has paid, across all investors — legitimate, since the Custodian is the actual paying institution, unlike an arbitrary investor who should never see another's).
- **`dashboards/trustee/TrusteeDashboard.tsx`** — gained a "Pending distributions" card: a review panel lists every investor's computed share (`investor: units — amount`) before the Trustee approves or rejects, so oversight is exercised with full visibility into what's about to be paid, not a blind rubber stamp.
- **`dashboards/investor/InvestorDashboard.tsx`** — gained a "My statements" card, reading `GET /profit-distributions` with the investor's own token; correctly shows only that investor's own records (verified live — see below).

## Findings

1. **A one-contract-per-cap-table design would have been a real privacy leak, caught by re-reading Daml's own privacy model before writing the template, not after.** The natural first design — one `ProfitDistribution` per distribution *event* (note + period), carrying the whole `shares : [DistributionShare]` list as a field — would have made every investor an observer on the *same* contract, meaning any one investor could read every other investor's distributed amount by simply looking at their own visible copy of it. Daml's privacy model has no field-level redaction: an observer sees the whole contract or none of it. Restructuring to create **one `ProfitDistribution` contract per investor share** (`forA shares $ \s -> create ProfitDistribution with ...` inside the approval choice) fixes this at the source — each investor is only ever an observer on their own record. This was verified, not just asserted: `distributionApprovalTest` includes `queryContractId investorB distributionACid === None` and a live backend-API check (see "Verified live") confirming investor A's statement list never contains investor B's contract ID. A genuinely important finding for a "production-grade fintech platform" claim, caught before it shipped rather than discovered as an incident later.

2. **`formatNGN` was still displaying 0 decimal places, despite `docs/implementation_plan.md` §3.6 explicitly requiring "2dp display formatting in the frontend" since the plan was written.** Every prior milestone's amounts happened to be round NGN figures (subscription minimums, target sizes, par values), so the gap was invisible until Milestone 7 introduced genuinely fractional pro-rata shares. Fixed by changing `Intl.NumberFormat`'s `maximumFractionDigits: 0` to `minimumFractionDigits: 2, maximumFractionDigits: 2`. Confirmed live: the Trustee's review panel correctly showed "₦1,000,000.00" and "₦500,000.00", not "₦1,000,000" and "₦500,000".

3. **No new "AI agent" this milestone**, unlike Milestones 2-6. `docs/implementation_plan.md`'s Milestone 7 bullet lists no AI line (the Reporting Agent is Milestone 8), and `docs/prompt.md`'s Risk Agent language ("concentration analysis") was already fully built in Milestone 6 for the allocation step — there's no analogous "distribution risk" concept in the spec to build a new agent around. Noted here only to make explicit that this wasn't an oversight.

## Verified live (not just automated tests)
Onboarded a fresh set of Milestone-7 orgs (Fund Manager, Issuing House, Shariah Advisor, Trustee, SEC, Distributor, Custodian) via the Operator's API, then scripted through propose → structure → finalize → Shariah-certify → Trustee-approve → submit-to-SEC → SEC-approve → issue via direct API calls (reusing the already-proven Milestones 2-5 chain) to reach an issued "Milestone 7 Verification Note" (₦100,000,000 Ijarah, 100 units at ₦1,000,000 par value). Scripted two investors through signup/KYC-verify/subscribe/allocate: Investor A allocated 10 units (₦10,000,000), Investor B allocated 5 units (₦5,000,000). Switched to UI-driven verification for the new pieces: logged in as the Custodian through the actual login form, confirmed the "Notes"/"Distributions" nav and all 16 issued notes in the session browsable, clicked "Propose distribution" on the test note, entered "Q1 2026" / ₦1,500,000, and confirmed "Pending requests (1)". Logged in as the Trustee, confirmed "Pending distributions (1)", clicked "Review", and confirmed the exact pro-rata breakdown rendered correctly — "Investor A: 10 units — ₦1,000,000.00" and "Investor B: 5 units — ₦500,000.00" (10:5 ratio of ₦1,500,000, hand-checkable) — before approving. Confirmed "Pending distributions (0)" afterward. Logged in as Investor A, confirmed the new "Statements" nav item and "My statements (1)". Queried `GET /profit-distributions` directly as both investors: Investor A's own list contained exactly one record (₦1,000,000, 10 units); Investor B's own list contained exactly one record (₦500,000, 5 units); Investor A's list did not contain Investor B's contract ID, live-confirming the privacy-isolation design decision (Finding #1) against the real API, not just the Daml Script test. No console errors, no failed network requests at any step.
