# Milestone 4 — Regulatory Submission & SEC Approval

Status: **gate met.** A product with an Approved Trustee review can have its Compliance Agent readiness re-checked, get a real AI-generated filing pack, be submitted to a chosen SEC org, and be approved (or rejected/withdrawn) on-ledger — verified live in a browser across two role logins (Issuing House, SEC), and with the compliance gate proven to actually block submission (not just preview it) via an automated test.

## Gate check (per docs/implementation_plan.md §4, Milestone 4)

| Requirement | Result |
|---|---|
| DAML: `RegulatorySubmission`, `SECApproval` — SEC as observer/controller | ✅ built as a 2-template propose-accept pair, sponsor + trustee kept as observers throughout so they can see the pending filing and the eventual approval |
| AI: Documentation Agent generates the filing pack (off-ledger, attached as documents) | ✅ real rule-based generator producing 4 grounded markdown documents (Term Sheet, Investment Summary, Approval Pack, Regulatory Filing), stored as `FilingDocument`s directly on the submission/approval contracts |
| Frontend: Issuing House submission flow, SEC dashboard | ✅ both built — filing pack preview + SEC picker on the Issuing House dashboard, a full review/approve/reject flow on a new SEC dashboard |
| **Gate: a reviewed product can be submitted and SEC-approved on-ledger** | ✅ proven twice: `dpm test` (2 new tests) + 4 backend integration tests (including a dedicated compliance-gate test), and live in a browser across both roles (see "Verified live" below) |

## What was built

### DAML (`daml/main/daml/AmanaX/Regulatory/Regulatory.daml`)
- Imports `AmanaX.Product.Types`, `AmanaX.Product.ProductStructure`, `AmanaX.Review.Review` — one-directional (Regulatory depends on Product and Review, neither depends back), so no circular-import trick was needed here unlike `Review.daml`.
- `RegulatorySubmission` (signatory Issuing House, observer SEC + sponsor + trustee) → `RegulatorySubmission_Approve` (controller SEC, creates `SECApproval` with an `approvalReference`) / `_Reject` (controller SEC, with a `rejectionReason`) / `_Withdraw` (controller Issuing House).
- `SECApproval` (signatories Issuing House + SEC, observer sponsor + trustee) — the terminal contract for this milestone; carries the full deal context plus the filing pack forward so any party with observer rights can see exactly what was approved and why.
- `FilingDocument` is a plain data record (`kind`, `title`, `markdown`) — not a template — embedded as a `[FilingDocument]` list field directly on both `RegulatorySubmission` and `SECApproval`. Simpler than modeling documents as their own contracts, and matches how Milestone 3's Compliance Agent output was already treated as off-ledger-generated-but-on-ledger-recorded content.
- Deal terms and both review stages' notes (`certificationNotes`, `approvalNotes`) are copied forward from `ProductStructure`/`TrusteeReview`, continuing the pattern established in Milestones 2-3 — the SEC reviews a filing entirely from the one contract it's an observer/signatory on.
- `daml/test/daml/AmanaX/Regulatory/RegulatoryWorkflowTest.daml` — `regulatorySubmissionApprovalTest` (full lifecycle, asserts sponsor and trustee can see the pending submission as observers, asserts the final `SECApproval`'s document count and `approvalReference`) and `withdrawAndRejectSubmissionTest` (withdraw, reject, and a `submitMustFail` proving a withdrawn submission can't be approved after the fact).

### Backend (`backend/src/`)
- `ledger/regulatory.ts` — domain wrapper following the same shape as `ledger/reviews.ts`: `listSubmissions` merges `RegulatorySubmission` + `SECApproval` query results into one array tagged `status: "Pending" | "Approved"`, `submitToSEC`, `approveSubmission`, `rejectSubmission`, `withdrawSubmission`. All `Decimal`/`Int` fields `.toString()`'d in `createArguments`/`choiceArgument`, continuing the JSON Ledger API encoding rule from every prior milestone.
- `api/regulatory.ts` — REST endpoints, with the milestone's central design decision: **the Compliance Agent's `readyForSubmission` becomes a real server-side gate, not just a preview.** `POST /trustee-reviews/:contractId/generate-filing-pack` (Issuing House) calls the agents service (`intent: "generate-documents"`) purely for preview and does not touch the ledger. `POST /trustee-reviews/:contractId/submit-to-sec` (Issuing House) **re-runs** the compliance check server-side immediately before submitting — if `!compliance.readyForSubmission`, it returns `409` with `{error, compliance}` and does not call `submitToSEC` at all, regardless of what the client believed the state to be. Only on a fresh pass does it regenerate the filing pack and submit. `GET /regulatory-submissions` is readable by every role with a legitimate interest (Issuing House, SEC, Fund Manager, Issuer, Trustee); approve/reject are SEC-only; withdraw is Issuing-House-only.
- `index.ts` — wires the new `regulatoryRouter` alongside the existing routers.
- `agents/client.ts`'s existing `invokeIssuingHouseAssistant` helper (from Milestone 2) is reused unchanged for both the filing-pack-generation and compliance-recheck calls — no new agents-service wiring needed.
- Tests (`test/regulatory.test.ts`): filing-pack preview (asserts all 4 document kinds with grounded content), the full lifecycle (submit → approve, asserting the sponsor and trustee can see the approval and that a Fund Manager attempting to approve gets `403`), a dedicated **compliance-gate test** that deliberately certifies/approves a review with thin notes and asserts `submitToSecRes.status === 409` with `compliance.readyForSubmission === false`, and withdraw/reject.

### Agents (`agents/src/`)
- `documentation/agent.ts` — rewritten from the Milestone 0 stub into a real generator: `runDocumentationAgent(context)` returns an array of 4 grounded markdown documents (Term Sheet, Investment Summary, Approval Pack, Regulatory Filing) built from `context.structure`/`shariahReview`/`trusteeReview` fields, with NGN currency formatting and graceful fallbacks ("TBD", "Untitled Product", "Not yet certified"/"Not yet approved") when upstream data is thin. `sourceFacts` records which fields fed each document, so the output stays traceable to real ledger state rather than reading as generic boilerplate.
- `types.ts` — `InvokeResponse.output` widened from a singular `GeneratedDocument` to `StructuringRecommendation | ComplianceAssessment | GeneratedDocument[]`, since the Documentation Agent now returns the whole filing pack in one call rather than one document at a time.
- `graph/issuingHouseAssistant.ts` — `documentationNode`'s model label updated from `"stub-milestone-0"` to `"rule-based-v1"`, matching the Structuring and Compliance agents' labels from Milestones 2-3.
- `test/documentationAgent.test.ts` (new) — 5 tests: fixed document order, grounded term-sheet content, approval-pack bundling of both stages' notes, the "not yet certified/approved" fallback path, and a graceful empty-structure fallback.
- `test/issuingHouseAssistant.test.ts` — updated the `generate-documents` graph test to assert `Array.isArray(res.body.output)` and the 4-document order, replacing the old single-document assertion.

### Frontend (`frontend/src/`)
- `api/regulatoryApi.ts` (new) — `FilingDocument`, `RegulatorySubmissionItem`, `FilingPackResponse`, `ComplianceGateError` interfaces plus the 5 API calls (`generateFilingPack`, `submitToSEC`, `listRegulatorySubmissions`, `approveRegulatorySubmission`, `rejectRegulatorySubmission`, `withdrawRegulatorySubmission`).
- `hooks/useRegulatorySubmissions.ts` (new) — the same fetch-hook-owns-state pattern used by every prior milestone's hooks.
- `dashboards/sec/SecDashboard.tsx` (rewritten from the Milestone 1 `RolePlaceholder`) — stat tiles (pending/approved counts), a pending-filings table with a "Review" action opening a deal-summary panel (description, Shariah certification notes, Trustee approval notes, min. subscription — all carried forward from earlier stages) plus a collapsible per-document list and an approve/reject form.
- `dashboards/issuingHouse/IssuingHouseDashboard.tsx` — the compliance panel (from Milestone 3) is restructured from a plain conditional block into an IIFE so the new filing-pack/submit-to-SEC UI has access to the `TrusteeReview` object it needs. When `compliance.readyForSubmission` is true, a "Generate filing pack" button appears; once generated, the 4 documents render in the same collapsible-`<details>` style as the SEC dashboard, followed by an SEC-picker form that calls `submit-to-sec`. A `409` response is caught, parsed, and re-displayed as a live "no longer ready" compliance readout — proving the gate is enforced even if the UI's own state goes stale. A new "Regulatory submissions" card lists the Issuing House's own filings with a withdraw action on pending ones.
- Both dashboards' `.module.css` files gained matching `.documentsList`/`.documentItem`/`.documentMarkdown` classes for the collapsible document previews.

## Findings

1. **Two self-caught authoring mistakes in `api/regulatory.ts` before they ever reached a build.** A stray `#`-style comment line (should have been `//`) and an import from a nonexistent `./reviews.types.js` module (the `ComplianceAssessment` shape needed to be a local interface mirroring `agents/src/types.ts`'s schema, not a cross-service import — the backend and agents services deliberately don't share a package). Both caught by re-reading the file before running `tsc`, not by the compiler itself finding them first. No behavioral impact since neither was ever committed or run.

2. **`Write` tool requires reading a file first even when fully replacing it.** Attempting to `Write` a full replacement for the existing `SecDashboard.tsx` placeholder failed with a "file not read yet" error; fixed by `Read`-ing the placeholder first, then writing the replacement. A process note, not a product defect.

3. **The compliance gate is a genuine server-side re-check, not a trust-the-client shortcut — deliberately tested for.** Milestone 3 exposed `readyForSubmission` only as a preview the Issuing House could look at. This milestone's `POST /trustee-reviews/:id/submit-to-sec` re-runs the same Compliance Agent call server-side at submission time and only proceeds past a fresh `readyForSubmission: true`. This was proven with a dedicated test (deliberately thin certification/approval notes → `409` + `compliance.readyForSubmission === false`) rather than relying on code review alone, since a gate that's only correct by inspection is exactly the kind of thing that silently regresses.

## Verified live (not just automated tests)
Onboarded a fresh set of Milestone-4 orgs (Fund Manager, Issuing House, Shariah Advisor, Trustee, SEC) via the Operator's API, then scripted through propose → structure → finalize → Shariah-certify → Trustee-approve via direct API calls (reusing the already-proven Milestones 2-3 chain) to reach an Approved Trustee review quickly. Switched to UI-driven verification for the new pieces: logged in as the Issuing House, confirmed the new "Filings" nav item and an empty "Regulatory submissions (0)" card, clicked "Check compliance" and got "Ready for submission" with zero gaps and a real Ijarah-specific document checklist. Clicked "Generate filing pack" and confirmed all 4 documents appeared with real grounded content (₦800,000,000 target size, 36-month tenor, quarterly lease rental — all pulled from the actual deal, not placeholders) rather than generic boilerplate. Selected the SEC org from the picker and submitted; the "Regulatory submissions" card updated to show it as "Pending" with a working withdraw button. Logged out, logged in as the SEC org, confirmed correct role-based routing to `/dashboard/sec` and "Pending filings (1)". Clicked "Review" and confirmed the full deal summary — including the Shariah certification notes and Trustee approval notes carried forward from earlier stages — plus all 4 filing documents in collapsible previews. Entered an approval reference (`SEC/AMX/2026/0001`) and approved; the dashboard updated to "Pending filings (0)" / "Approved (1)" with the correct product name, structure type, and approval reference in the Approved table. The compliance-gate-blocks-submission behavior (Finding 3) was proven via the automated `regulatory.test.ts` case rather than re-demonstrated live in the browser, since the automated test exercises the exact server-side re-check path precisely and a live repeat would add no additional confidence.
