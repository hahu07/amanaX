# Milestone 3 — Shariah & Trustee Review

Status: **gate met.** A Finalized structure can be submitted for Shariah certification, certified, chained straight into Trustee review, approved, and checked for SEC-submission readiness by the AI Compliance Agent — all verified live in a browser across four role logins (Issuing House, Shariah Advisor, Trustee, back to Issuing House), not just via automated tests.

## Gate check (per docs/implementation_plan.md §4, Milestone 3)

| Requirement | Result |
|---|---|
| DAML: `ShariahReview`, `TrusteeReview` — certification choices, observer visibility for downstream roles | ✅ built as a 4-template propose-accept pair (`ShariahReviewRequest`→`ShariahReview`, `TrusteeReviewRequest`→`TrusteeReview`), sponsor as observer throughout |
| Frontend: Shariah Advisor and Trustee dashboards | ✅ both replace their Milestone 1 placeholders with real functionality on the shared design system |
| AI: Compliance Agent readiness checklist wired in | ✅ real rule-based engine (not the Milestone 0 stub), reachable from the Issuing House once a Trustee review is Approved |
| **Gate: a structured product can be Shariah-certified and Trustee-reviewed on-ledger** | ✅ proven twice: `dpm test` (7 tests) + 14 backend integration tests, and live in a browser across all four roles (see "Verified live" below) |

## What was built

### DAML (`daml/main/daml/AmanaX/Review/Review.daml`)
- All four templates live in **one module**, not split like `Product`'s `Types`/`ProductProposal`/`ProductStructure` — `ShariahReview` needs `ContractId TrusteeReviewRequest` as a choice return type (to chain straight into Trustee review) and `TrusteeReviewRequest` needs `ContractId ShariahReview` as a field type, which would be a circular module import if split. Documented inline as the reason for the unusual structure.
- `ShariahReviewRequest` (signatory Issuing House, observer Shariah Advisor + sponsor) → `ShariahReviewRequest_Certify` (controller Shariah Advisor, creates `ShariahReview` with **both** as signatories) / `_Reject` / `_Withdraw`.
- `ShariahReview` (signatories Issuing House + Shariah Advisor, observer sponsor) → `nonconsuming choice ShariahReview_SubmitForTrusteeReview` (controller Issuing House) creates `TrusteeReviewRequest` with `shariahReviewCid = self`. This is a **real choice on the certified contract**, not a plain create — Step 6 is structurally impossible to reach without a `ShariahReview` in hand, not just a UI convention.
- `TrusteeReviewRequest` → `TrusteeReviewRequest_Approve` (controller Trustee, creates `TrusteeReview`) / `_Reject` / `_Withdraw` — same shape as the Shariah stage.
- Deal terms (`productName` … `redemptionTerms`) are copied forward at every stage from `ProductStructure`, the same pattern `ProductStructure` itself already uses for `ProductProposal`'s fields — a Shariah Advisor or Trustee reviews a deal entirely from the one contract they're an observer/signatory on, with no need for separate read access to `ProductStructure`.
- **Step 1 (submit for Shariah review) is a plain `createCmd`, not a choice on `ProductStructure`** — `ProductStructure.daml` deliberately does not import the Review module (Review → Product is the only direction that doesn't cycle), so it cannot host a choice returning a Review-module type. The "structure must be Finalized" rule is enforced in the backend route, not the ledger — a deliberate, documented trade-off (see Findings).
- `daml/test/daml/AmanaX/Review/ReviewWorkflowTest.daml` — `shariahAndTrusteeReviewTest` (full lifecycle, asserting the sponsor can see both the pending request and the final approved review as an observer) and `rejectAndWithdrawTest` (reject, withdraw, and a `submitMustFail` proving a withdrawn request can't be certified after the fact).
- `AmanaX.Identity.Organization`'s `OrgRole` gained `Issuer` mid-Milestone-2 (see the `338476a` commit, before this milestone started) — `onboardsEveryOrgRoleTest` now onboards 8 roles, not 7.

### Backend (`backend/src/`)
- `ledger/reviews.ts` — domain wrappers for both stages, each list function merging its Request + final-Review query results into one array tagged `status: "Pending" | "Certified"` (or `"Approved"`), so the frontend gets one unified list per stage instead of having to know about the two-template split.
- `ledger/products.ts` — added `findStructureById`, needed to look up a structure's copied fields when submitting it for Shariah review.
- `api/reviews.ts` — REST endpoints for both stages plus the compliance-check route. `POST /structures/:id/submit-shariah-review` looks up the structure server-side (never trusts client-supplied deal terms) and returns `409` if it isn't Finalized. `POST /trustee-reviews/:id/compliance-check` is `IssuingHouse`-only and only matches an *approved* `TrusteeReview` (`findApprovedTrusteeReviewById` can't find a still-pending request), so Step 7 structurally can't run before Step 6 completes.
- `vitest.config.ts` — added `testTimeout`/`hookTimeout: 30000`. See Findings.
- Tests (`test/reviews.test.ts`): the full lifecycle (submit → certify → submit-for-trustee → approve → compliance-check, asserting `readyForSubmission: true` and a real structure-specific document checklist), a 409 guard test, and reject/withdraw.

### Agents (`agents/src/compliance/agent.ts`)
- Replaced the Milestone 0 stub with a real, deterministic, rule-based readiness checker (same "not LLM-backed yet, isolated behind one function" reasoning as Milestone 2's Structuring Agent):
  - `workflowGaps` — missing structure/Shariah/Trustee stages, plus a substantiveness check on the Trustee's own approval notes (<20 chars flagged).
  - `shariahChecklistGaps` — a substantiveness check on the Shariah certification notes.
  - `missingDocuments` — a baseline SEC-filing checklist (Trust Deed, Shariah Pronouncement, Information Memorandum) plus **structure-type-specific** documents grounded in what that instrument actually needs (Ijarah → Asset Valuation Report + Lease Agreement; Murabahah → Purchase Agreement; etc.) — informational, not blocking, since no document-generation system exists yet (that's the Documentation Agent, a later milestone).
  - `readyForSubmission` — true only when `blockingIssues` (the workflow gaps) and `shariahChecklistGaps` are both empty; a full-but-thin set of notes is correctly flagged as not ready even though every stage technically exists.
- `graph/issuingHouseAssistant.ts` — the `compliance` node's `model` label updated from `"stub-milestone-0"` to `"rule-based-v1"`.
- New test file `test/complianceAgent.test.ts` — 5 tests covering the empty-state, the fully-ready case, thin-notes detection, the structure-specific document checklist, and confirming missing documents alone don't block readiness.

### Frontend (`frontend/src/`)
- `api/reviewsApi.ts`, `hooks/useShariahReviews.ts`, `hooks/useTrusteeReviews.ts` — same fetch-hook-owns-state pattern as every prior milestone.
- `dashboards/shariahAdvisor/ShariahAdvisorDashboard.tsx` — stat tiles, a pending-reviews table with a "Review" action opening a deal-summary panel (description, profit mechanism, redemption terms, min. subscription) plus a certify/reject form, and a read-only certified-reviews table showing the certification notes.
- `dashboards/trustee/TrusteeDashboard.tsx` — same shape, with the pending-review panel additionally showing the **Shariah certification notes carried forward**, so the Trustee reviews with full context from one contract.
- `dashboards/issuingHouse/IssuingHouseDashboard.tsx` — Finalized structures gain a "Submit for Shariah review" action (hidden once a review already exists for that structure, via `shariahReviews.data.some(r => r.structureCid === s.contractId)`); two new cards (Shariah reviews, Trustee reviews) with a "Submit for Trustee review" action on Certified Shariah reviews (same already-submitted guard); the Trustee-reviews card's Approved rows get a "Check compliance" action rendering the full `ComplianceAssessment` (workflow gaps / Shariah checklist gaps / document checklist) inline.
- Both `ShariahAdvisorDashboard` and `TrusteeDashboard` replace their Milestone 1 `RolePlaceholder` wrappers entirely.

## Findings

1. **A real cross-role UI-placement bug, caught only by live browser verification.** The backend correctly gates `POST /trustee-reviews/:id/compliance-check` to `IssuingHouse` (matching docs/prompt.md's Step 7 → Step 8: the Issuing House checks readiness before *it* submits to SEC) — but the "Check compliance" button was first wired into the **Trustee** dashboard by a copy-paste-driven mistake while building it right after Trustee's approve/reject form. Automated tests didn't catch this (`test/reviews.test.ts` correctly calls the endpoint with `issuingHouseToken`, since I wrote the test correctly even though I wired the UI wrong). Live-testing as the Trustee produced a `403 Forbidden` network error with no visible UI feedback (the panel just stayed empty) — caught by checking `preview_network` after the panel didn't populate, not from any error message. Fixed by moving the entire compliance-check UI (state, handler, CSS) from `TrusteeDashboard` to `IssuingHouseDashboard`'s Trustee-reviews card. This is the second milestone in a row where live multi-role browser verification caught a defect that a green automated-test suite did not (Milestone 2's Finding 5 was the first) — reinforcing that this is a structural blind spot of integration tests that drive the REST API directly rather than the actual per-role frontend, not a one-off.

2. **A stale test-data bug in `reviews.test.ts` itself**, caught before it reached a "passing but wrong" state: the first draft of the full-lifecycle test fetched the Shariah Advisor's/Trustee's party via `GET /orgs` + `.find(o => o.role === "ShariahAdvisor")` inside each test, rather than using the party already returned by that test's own `beforeAll` onboarding call. Against this long-running dev sandbox (accumulating organizations across every milestone's manual verification and every re-run of the test suite itself), `.find()` would sometimes match a **different, stale** `ShariahAdvisor` org from an earlier run instead of the current run's — so the review got submitted to a party the test's own `shariahAdvisorToken` didn't correspond to, and the follow-up `GET /shariah-reviews` (correctly scoped to the actual logged-in party) came back empty. Fixed by capturing `shariahAdvisorParty`/`trusteeParty` directly from `onboardOrgAndLogin`'s return value instead of re-deriving them. Lesson for future test files against this sandbox: never re-look-up a party you already have from onboarding.

3. **Default Vitest timeouts (5s test / 10s hook) are too tight for tests that chain many sequential ledger round-trips.** The full Shariah→Trustee lifecycle test alone is 10+ ledger commands in one test; against an increasingly large dev sandbox (many hours of accumulated contracts across every milestone in this session), both the per-test and `beforeAll`-hook default timeouts started failing intermittently. Fixed with `testTimeout`/`hookTimeout: 30000` in `vitest.config.ts` — a deliberate acknowledgment that these are integration tests against a real, and in this dev environment increasingly loaded, ledger, not unit tests.

4. **Unrelated system-level resource contention mid-milestone.** A different project on the same machine (`~/Canton/vetify`) had a process leak (an MCP server process respawning every ~15s without cleaning up the previous instance, 44+ accumulated) that caused intermittent `Stream closed` failures for shell commands in this session. Not caused by or related to AmanaX; resolved itself before it required intervention. Noted here only because it interrupted this milestone's work and is worth recognizing quickly (via `ps aux` process counts) if similar unexplained tool failures recur.

## Verified live (not just automated tests)
Onboarded a Fund Manager, Issuing House, Shariah Advisor, and Trustee org+user via the Operator's API. As the Fund Manager, proposed a product; as the Issuing House, structured and finalized it, then clicked "Submit for Shariah review" and picked the Shariah Advisor from the live org directory. Signed in as the Shariah Advisor: saw the pending review with the full deal summary, entered certification notes, and certified it — watched it move from "Pending reviews (1)" to "Certified (1)" with the notes displayed. Back as the Issuing House: the Shariah review showed "Certified" with a "Submitted for review" badge correctly replacing the resubmit button; clicked "Submit for Trustee review" and picked the Trustee. Signed in as the Trustee: saw the pending review **including the Shariah Advisor's certification notes carried forward**, entered approval notes, and approved — moved to "Approved (1)". Back as the Issuing House: clicked "Check compliance" on the approved review and got a live `readyForSubmission: true` assessment with the correct Ijarah-specific document checklist (Trust Deed, Shariah Pronouncement, Information Memorandum, Asset Valuation Report, Lease Agreement). Along the way, caught the compliance-check RBAC/UI-placement bug (Finding 1) via a `403` in the network log when it was still wired to the Trustee dashboard, fixed it, and re-verified the corrected placement live.
