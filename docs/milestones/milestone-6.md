# Milestone 6 — Investor Onboarding, Subscription, Allocation

Status: **gate met.** An investor can self-register, get KYC-verified by a Distributor, subscribe to an issued Investment Note, and be allocated a real, standard-compliant `Holding` — verified live in a browser across three role logins (public signup, Distributor, Investor), with the `Holding` interface query proven directly in a Daml Script test, not just structurally similar to one.

## Gate check (per docs/implementation_plan.md §4, Milestone 6)

| Requirement | Result |

## What was built

### DAML
- **`daml/main/daml/AmanaX/Investor/InvestorProfile.daml`** (new) — `InvestorProfile` is both the identity record (a freshly-allocated, platform-managed party per investor — Investor is deliberately *not* an `OrgRole`; see the module comment on `AmanaX.Identity.Organization.OrgRole`) and the KYC record, in one template. `KycStatus = KycPending | KycVerified | KycRejected`. `InvestorProfile_Verify`/`_Reject` are controlled by the investor's chosen Distributor.
- **`daml/main/daml/AmanaX/Subscription/Subscription.daml`** (new) — `SubscriptionRequest` (signatory investor, observer distributor/issuingHouse/sponsor) → `_Withdraw` / `_Reject` / `_Allocate` (controller distributor, creates `Allocation`). Same propose-accept shape, same "both templates in one module because the choice's result type needs it" reasoning as `Review.daml` and `Regulatory.daml`. Deal facts (symbol, productName, structureType, tenorMonths, parValueNGN, targetSizeNGN, minSubscriptionNGN) are copied forward from the `InvestmentNote`, continuing the copy-forward pattern from every prior stage.
- **`Allocation`** — signatory **distributor**, not issuingHouse (the Distributor is the controller of `SubscriptionRequest_Allocate`, so its authority is what's actually available to sign the new contract without a separate `actAs`; this also matches real-world placement-agent practice). `interface instance Holding for Allocation` genuinely implements the CIP-0056 `Holding` interface (`owner`, `instrumentId`, `amount`, `lock = None`, `meta`) — no `xImpl` functions needed since `Holding` defines no choices, just a view.
- **`daml/main/daml/AmanaX/Issuance/Issuance.daml`** (modified) — `InvestmentNote` gained an `operator : Party` field and observer. Needed because an Investor has no stakeholder relationship to any note until allocated one, so there was no party the backend could browse "available offerings" through; the Platform Operator (already the broad-visibility administrative party for Organization/User) fills that role. This is a genuine schema change to a Milestone 5 template, made because Milestone 6 revealed a real gap in Milestone 5's own "discoverable" claim — the same kind of honest correction as Findings #1 in milestone-5.md.
- `daml/test/daml/AmanaX/Investor/InvestorProfileTest.daml` — `verifyAndRejectTest`, `onlyDistributorCanDecideTest`.
- `daml/test/daml/AmanaX/Subscription/SubscriptionWorkflowTest.daml` — `subscriptionAllocationTest` (full lifecycle from proposal through allocation, then `holdings <- queryInterface @Holding investor` asserting the returned `HoldingView` matches exactly — the literal Daml-level proof of the gate), `withdrawAndRejectSubscriptionTest`.
- `daml/test/daml.yaml` already had the `splice-api-token-holding-v1` data-dependency from Milestone 5; no new vendor dependency needed.

### Agents (`agents/src/risk/agent.ts`, new)
- `runRiskAgent(context)` — deterministic, rule-based: **concentration tier** (allocation amount ÷ offering target size — Low/Medium/High), **product risk tier** (a structure-type base rating — Murabahah lowest, Mudarabah highest, reflecting fixed-markup vs. profit-sharing risk — bumped up for long tenors), **operational flags** (below minimum subscription, would exceed target size), and an **overall risk** rating (the worse of the two tiers, bumped to at least Medium if any operational flag fired).
- Deliberately **not** wired into the existing Issuing House Assistant supervisor graph (`graph/issuingHouseAssistant.ts`) — that graph is scoped to the Issuing House persona and three specific workflow steps (Structuring, Compliance, Documentation) per `docs/implementation_plan.md` §6. The Risk Agent runs for a different persona (Distributor) at a different step (Step 13, allocation), so it's a separate, dedicated `POST /internal/risk/assess` endpoint rather than a fourth graph node reachable through the wrong persona's route.
- Advisory only — docs/prompt.md's own language distinguishes the Compliance Agent ("*Checks* regulatory readiness" — a real blocking gate since Milestone 4) from the Risk Agent ("*Assists with* risk assessment" — deliberately not blocking). Nothing in the backend rejects an allocation based on the Risk Agent's output.
- `test/riskAgent.test.ts` — 5 tests covering concentration tiers, product-risk tenor bumps, and both operational flags.

### Backend
- **`ledger/investors.ts`** (new) — `createInvestorProfile` (allocates a fresh party, mirrors `createOrganization`), `listInvestorProfiles`, `findInvestorProfileByEmail`/`ById`, `verifyInvestorProfile`, `rejectInvestorProfile`.
- **`ledger/subscriptions.ts`** (new) — `createSubscriptionRequest`, `listSubscriptions` (merges Pending/Allocated), `findSubscriptionById`, `sumAllocatedNGN` (sums every existing `Allocation` for an instrument via the Issuing House's party — the one stakeholder that observes every `Allocation` regardless of which Distributor created it), `allocateSubscription`, `rejectSubscription`, `withdrawSubscription`.
- **`ledger/regulatory.ts`** gained `findApprovalById`; **`ledger/issuance.ts`**'s `InvestmentNote` interface and `issueNote()` gained the `operator` field (see the DAML section above).
- **`api/investorSignup.ts`** (new, public — no `requireAuth`) — `GET /distributors` (minimal directory for the signup form), `POST /investor-signup`. The one genuinely self-service identity flow in this system; every other role is Platform-Operator-onboarded.
- **`api/investors.ts`** (new, authenticated) — `GET /investor-profiles` (Investor/Distributor/PlatformOperator; Daml's own stakeholder visibility does the per-party filtering, no special-casing needed except routing PlatformOperator to its own party), `POST /investor-profiles/:id/verify`/`reject` (Distributor only).
- **`api/subscriptions.ts`** (new, authenticated) — `POST /investment-notes/:id/subscribe` (Investor; re-derives distributor from the investor's own verified `InvestorProfile` and every deal fact from the on-ledger `InvestmentNote`, never trusting client input), `GET /subscriptions`, `POST /subscriptions/:id/risk-check` (preview, Distributor), `POST /subscriptions/:id/allocate` (Distributor — see the oversubscription note below), `/reject`, `/withdraw`.
- **`api/issuance.ts`** — `GET /investment-notes` and its metadata endpoint now special-case the `Investor` role: they query via the Platform Operator's party instead of the investor's own (an investor has no stakeholder visibility into a note until allocated one).
- **A real, server-enforced oversubscription guard** — distinct from the Risk Agent's advisory concentration tier. `POST /subscriptions/:id/allocate` sums every existing `Allocation` for the instrument and returns `409` if the requested allocation would push the total past the note's `targetSizeNGN`. This is treated as a hard rule (a fixed-size offering allocating more than its target size is a real regulatory problem), not a risk judgment call the Distributor should be free to override — the same "genuine business rule gets a real gate, not just advice" reasoning already applied to the Compliance Agent's submission gate in Milestone 4.
- **`auth/types.ts`** — `Role` widened to include `"Investor"`, which is not an `OrgRole` (see the DAML section). `api/auth.ts`'s login route now also checks `InvestorProfile` by email after `User`.
- **`index.ts`** — `investorSignupRouter` had to be registered *before* every `requireAuth`-gated router (see Findings #2) — a real routing bug caught and fixed during this milestone, not a design decision.
- **`express-async-errors`** added as a dependency, plus a catch-all error-handling middleware in `index.ts` — see Findings #3.

### Frontend
- **`api/investorsApi.ts`**, **`api/subscriptionsApi.ts`** (new) — typed clients following the established `apiFetch` pattern; `listPublicDistributors`/`signupInvestor` pass `null` for the token (public routes).
- **`hooks/useInvestorProfiles.ts`**, **`hooks/useSubscriptions.ts`** (new) — the standard fetch-hook-owns-state pattern used by every prior milestone's hooks.
- **`pages/InvestorSignupPage.tsx`** (new) — the one public, pre-login identity flow in the app; reuses `LoginPage.module.css` for visual consistency. Linked from `LoginPage.tsx` ("New investor? Create an account").
- **`dashboards/investor/InvestorDashboard.tsx`** (rewritten from `RolePlaceholder`) — KYC status banner/badge, a browsable "Available notes" table (subscribe action gated on `KycVerified`, hidden once already subscribed to that note), "My subscriptions" (pending, with withdraw), "My holdings" (allocated, showing units).
- **`dashboards/distributor/DistributorDashboard.tsx`** (rewritten from `RolePlaceholder`) — "Investor KYC" table with a review panel (verify/reject), "Subscriptions" table with a review panel showing the AI Risk Agent's live assessment (concentration/overall-risk badges, operational flags) before an allocate/reject decision, "Allocated" read-only history.
- **`auth/types.ts`** — `Role` widened to include `"Investor"`, `ROLE_ROUTE`/`ROLE_LABEL` gained an `Investor` entry. `App.tsx`'s `/dashboard/investor` route is now genuinely `ProtectedRoute`-gated (it was an open, unauthenticated route since Milestone 1, explicitly noted as "kept reachable for UI review" pending this milestone).

## Findings

1. **The plan's own Milestone 6 wording conflated two different meanings of "Allocation," and needed correcting before writing any code — not after, this time.** `docs/prompt.md`'s template list and `docs/implementation_plan.md`'s decision log both say `Allocation` "implements Holding + Allocation/Allocation Instruction interfaces." Reading `splice-api-token-allocation-v1`'s `AllocationV1.daml` before designing anything showed that CIP-0056's `Allocation` interface models a **temporary reservation of a Holding for one leg of a cross-app atomic settlement** (a DVP protocol coordinating an executor, sender, and receiver across potentially different registries — `Allocation_ExecuteTransfer`, `Allocation_Cancel`, `Allocation_Withdraw`, with `SettlementInfo.executor` as a third party). That is a different concept from "the units this investor was allocated in AmanaX's own single-registry issuance" — the domain meaning of "allocation" in a Sukuk/Murabahah offering. Building the full settlement-coordination interface (plus `AllocationInstruction`, `TransferInstruction`, and their `Factory` counterparts) for a closed-loop workflow with no second registry to settle against would have been pure unused surface area — interface methods with no real caller, satisfying the letter of the plan's wording while adding nothing anyone could exercise. The template named `Allocation` in this codebase implements only `Holding` (a real, useful, and directly-tested interface), not the CIP-0056 `Allocation` family. Both `docs/implementation_plan.md`'s decision-log row and the plan text are left as historical record; this file is the correction, following the same pattern as milestone-5.md's Finding #1.

2. **A real routing bug, caught by directly debugging a 401 on a route with no auth middleware attached to it.** `investorSignupRouter` was registered on `app` after several routers with an unconditional `router.use(requireAuth)`. Express runs *every* mounted router's own middleware for *every* request that reaches it — not just requests matching that router's own routes — so `orgsRouter`'s `requireAuth` (registered earlier) intercepted and 401'd requests to `/investor-signup` before they ever reached the router that actually owned that route, even though `investorSignupRouter` itself has no auth middleware at all. This had never surfaced before because every prior milestone's public routes (`/health`, `POST /auth/login`) were registered *before* any `requireAuth`-gated router; this was the first milestone to add a public route *after* one. Fixed by moving `investorSignupRouter`'s registration ahead of every `requireAuth`-gated router, with a comment explaining why the order matters — a subtlety worth flagging for any future public route.

3. **A real, previously-latent stability gap, discovered by directly crashing the dev backend.** While manually testing the fix for Finding #2 with a deliberately bad `distributor` party string, the resulting ledger error came back as an *unhandled promise rejection* — Express 4 does not route a rejected promise from an `async` route handler to error-handling middleware on its own, and Node terminates the process on an unhandled rejection by default. The backend crashed outright instead of returning a 500. This was a pre-existing gap across every prior milestone's routes (none of them wrap ledger calls in try/catch), just never triggered because no test or manual walkthrough had sent genuinely invalid data to a route with no upstream validation catching it first. Fixed with the `express-async-errors` package (one import, changes no existing route code) plus a catch-all error-handling middleware in `index.ts` returning a generic 500. A minimal, proportionate fix — not a wider hardening pass, which stays scoped to Milestone 9 as planned — but one directly justified by a crash that would otherwise have taken down every future milestone's dev server the same way.

## Verified live (not just automated tests)
Onboarded a fresh set of Milestone-6 orgs (Fund Manager, Issuing House, Shariah Advisor, Trustee, SEC, Distributor) via the Operator's API, then scripted through propose → structure → finalize → Shariah-certify → Trustee-approve → submit-to-SEC → SEC-approve → issue via direct API calls (reusing the already-proven Milestones 2-5 chain) to reach an issued "Milestone 6 Verification Note" (₦50,000,000 Murabahah, 50 units at ₦1,000,000 par value). Switched to UI-driven verification for the new pieces: opened the public `/investor-signup` page (unauthenticated), confirmed the live Distributor directory populated correctly, and created an account for "Amina Bello." Logged in as her through the actual login form and confirmed the Investor dashboard showed "KYC status: Pending," all 16 issued notes in the session browsable but marked "KYC required," and correct nav/routing. Logged in as the Distributor and confirmed her pending KYC appeared; clicked "Verify KYC" and confirmed the count moved from "1 pending" to "0 pending / 1 verified." Logged back in as Amina, confirmed the note's action changed from "KYC required" to "Subscribe," submitted a ₦5,000,000 subscription, and confirmed "My subscriptions (1)." Logged back in as the Distributor, clicked "Review" on the pending subscription, and confirmed the **AI Risk Agent** returned a live, grounded assessment — "This allocation represents 10.0% of the offering (medium concentration). The Murabahah structure over 12 months carries low product risk. No operational flags raised." — with the concentration percentage exactly matching ₦5,000,000 ÷ ₦50,000,000. Allocated the full amount and confirmed "Allocated (1)." Logged back in as Amina one final time and confirmed "Holdings: 1" and "My holdings (1)" — her real, on-ledger `Holding` of the issued note. No console errors, no failed network requests at any step.
