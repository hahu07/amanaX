# Milestone 5 — Issuance & Token Standard Metadata

Status: **gate met.** An SEC-approved product can be issued by the Issuing House into a live `InvestmentNote` carrying a real Token Standard `InstrumentId` and well-known-keyed `Metadata`, discoverable both as part of the full note and via a dedicated CIP-0056-shaped metadata endpoint — verified live in a browser across three role logins (Issuing House, and cross-checked as Fund Manager/Trustee/SEC), not just via automated tests.

## Gate check (per docs/implementation_plan.md §4, Milestone 5)

| Requirement | Result |
|---|---|

## What was built

### DAML (`daml/main/daml/AmanaX/Issuance/Issuance.daml`)
- Imports `AmanaX.Product.Types`, `AmanaX.Regulatory.Regulatory` (for `SECApproval`), and the vendored `Splice.Api.Token.HoldingV1` / `Splice.Api.Token.MetadataV1` packages.
- `InvestmentNote` (signatory Issuing House, observer SEC + sponsor + trustee) carries `instrumentId : InstrumentId` (`admin = issuingHouse`, `id = symbol`), `meta : Metadata` (well-known `amanax.io/*` keys), plus the deal terms and `approvalReference` copied forward from the `SECApproval`, and a `parValueNGN`/`totalSupply` pair (`totalSupply = targetSizeNGN / parValueNGN`).
- `ensure` clause enforces `instrumentId.id == symbol` and `instrumentId.admin == issuingHouse` — a Daml-level guard against a mismatched `InstrumentId` (caught by `mismatchedInstrumentIdRejectedTest`), on top of the backend's own symbol-uniqueness check (see below).
- `investmentNoteMetadata` is a plain top-level function building the `Metadata` value, so the Daml Script tests and the (documented) real creation path can't drift on which keys get set.
- Same "plain `createCmd`, not a choice" trade-off as Milestone 3's Step 1 (submitting for Shariah review): a choice returning `ContractId InvestmentNote` would have to live on `SECApproval` in `Regulatory.daml`, which would force that module to import `Issuance.daml` — circular, since `InvestmentNote` already needs `ContractId SECApproval` as a field. The backend verifies the referenced `SECApproval` is active and belongs to the caller before creating this contract.
- `daml/test/daml/AmanaX/Issuance/IssuanceWorkflowTest.daml` — `issuanceTest` (full lifecycle from proposal through issuance, asserting sponsor and SEC can see the issued note as observers, and asserting the exact `Metadata` values) and `mismatchedInstrumentIdRejectedTest` (a `submitMustFail` proving the `ensure` clause rejects an `InstrumentId` that doesn't match the declared symbol/admin).
- `daml/test/daml.yaml` gained a direct data-dependency on the vendored `splice-api-token-holding-v1` dar — needed because the test file constructs `InstrumentId` values directly, not just through `AmanaX.*` modules like every prior test file.

### Backend (`backend/src/`)
- `ledger/issuance.ts` — domain wrapper following the `ledger/regulatory.ts` shape: `issueNote`, `listNotes`, plus two query-before-mutate helper finders (`findNoteByApprovalCid`, `findNoteBySymbol`) used only for the guards below — there are no contract keys under LF 2.1, so "one note per approval" and "unique symbol per Issuing House" (`HoldingV1.daml`'s own doc comment on `InstrumentId`) are both backend-level checks, the same trade-off already made for "already submitted" guards in Milestones 3-4.
- `ledger/regulatory.ts` gained `findApprovalById`, mirroring `reviews.ts`'s `findApprovedTrusteeReviewById` — needed to look up the `SECApproval`'s deal terms server-side at issuance time (never trusts client-supplied deal terms, same reasoning as `sponsorType` in `api/proposals.ts`).
- `api/issuance.ts` — `POST /sec-approvals/:contractId/issue` (Issuing House only; body `{symbol, parValueNGN}`, both genuinely new inputs — everything else is re-derived from the approval) returns `404` if the approval isn't found, `409` if it's already been issued, and `409` if the symbol is already in use by that Issuing House. `GET /investment-notes` and `GET /investment-notes/:contractId/metadata` are readable by the same role set as `GET /regulatory-submissions` (`IssuingHouse, SEC, FundManager, Issuer, Trustee`) — deliberately not a wider list, since `InvestmentNote` has the identical signatory/observer shape as `SECApproval` and any other role would just get an empty result.
- `index.ts` wires the new `issuanceRouter`.
- Tests (`test/issuance.test.ts`): issuance with real `InstrumentId`/`Metadata` assertions plus cross-role visibility (sponsor/trustee/SEC), a 403 RBAC test, a "blocks issuing the same approval twice" 409 test, and a "blocks reusing a symbol" 409 test.

### Frontend (`frontend/src/`)
- `api/investmentNotesApi.ts` (new) — `InstrumentId`, `InvestmentNote`, `TokenMetadata` interfaces plus `issueInvestmentNote`, `listInvestmentNotes`, `getInvestmentNoteMetadata`.
- `hooks/useInvestmentNotes.ts` (new) — the same fetch-hook-owns-state pattern as every prior milestone's hooks.
- `dashboards/issuingHouse/IssuingHouseDashboard.tsx` — Approved regulatory-submission rows gain an "Issue note" action (hidden behind an "Issued" badge once already issued, via `investmentNotes.data.some(n => n.approvalCid === s.contractId)`) opening a symbol/par-value form; a new "Investment Notes" card lists issued notes with total supply and par value.
- `dashboards/productSponsor/ProductSponsorDashboard.tsx`, `dashboards/trustee/TrusteeDashboard.tsx`, `dashboards/sec/SecDashboard.tsx` — each gains a read-only "Issued notes" / "Investment notes" card. These three (plus the Issuing House) are exactly the roles with any ledger-level visibility into `InvestmentNote` (its signatory/observer set), so no other dashboard was touched — Custodian and Distributor stay `RolePlaceholder`s, as `docs/implementation_plan.md` itself scopes their first real content to Milestones 6-7.

## Findings

1. **The plan's own Milestone 5 line overclaimed what the vendored Token Standard package offers, and needed correcting.** `docs/implementation_plan.md` (both the Milestone 5 bullet and the §5 decisions-log row) said `InvestmentNote` would "implement the Token Metadata interface" with "name/symbol/totalSupply." Reading the actual vendored `splice-api-token-metadata-v1` package (`vendor/token-standard/splice-api-token-metadata-v1/daml/Splice/Api/Token/MetadataV1.daml`) before writing any code showed it defines no such interface — only generic plumbing types (`Metadata`, a `TextMap Text`; `AnyValue`; `ChoiceContext`). The actual per-instrument identity concept in the Token Standard is `InstrumentId` (defined in `splice-api-token-holding-v1`'s `HoldingV1.daml`, attached to `Holding`s), not a metadata interface at all. Both docs are corrected in this commit: `InvestmentNote` adopts `InstrumentId` + `Metadata` (populated with `amanax.io/*` well-known keys, per `MetadataV1.daml`'s own k8s-style naming convention), which is the real shape Milestone 6's `Holding`/`Allocation` implementation will need to reference. Recorded here rather than silently building the "correct" thing and leaving the plan wrong, since a future session reading the plan without this note would repeat the same false assumption.

2. **No separate `ProductIssuance` template, unlike `docs/prompt.md`'s template list.** The spec lists `ProductIssuance` and `InvestmentNote` as two templates. Given Step 10 ("Investment Note is issued") is a single unilateral Issuing-House action with no counterparty approval step of its own (unlike Steps 5/6/9, which are genuine propose-accept pairs between two different parties), a separate `ProductIssuance` "request" template would have no controller to accept it — it would just be `InvestmentNote` under a different name. Built as one template, matching the precedent already set in Milestone 2 (`ProductStructure_Finalize` is a status flip on the same signatories, not a two-template pair, because finalizing needs no counterparty consent either).

3. **`InstrumentId` uniqueness is enforced at two layers, neither of them a ledger-level constraint.** `HoldingV1.daml`'s own doc comment says an instrument admin's `id` "MUST be unique and unambiguous" — but LF 2.1 has no contract keys (§2 of the implementation plan), so this can't be a hard ledger guarantee. It's enforced as: (a) a Daml `ensure` clause on `InvestmentNote` rejecting a self-inconsistent `InstrumentId` (`id` not matching the declared `symbol`, or `admin` not matching `issuingHouse`), and (b) a backend query-before-mutate check rejecting a symbol already used by that Issuing House. Both are best-effort, same as every other "already submitted" guard built in this session — a real ledger-level constraint would need LF 2.3+ contract keys, out of scope for this MVP's pinned SDK version.

## Verified live (not just automated tests)
Onboarded a fresh set of Milestone-5 orgs (Fund Manager, Issuing House, Shariah Advisor, Trustee, SEC) via the Operator's API, then scripted through propose → structure → finalize → Shariah-certify → Trustee-approve → submit-to-SEC → SEC-approve via direct API calls (reusing the already-proven Milestones 2-4 chain) to reach an Approved `SECApproval` for "Milestone 5 Verification Note" (₦800,000,000, 36-month Ijarah). Switched to UI-driven verification for the new piece: logged in as the Issuing House through the actual login form, confirmed the new "Notes" nav item and an empty "Investment Notes (0)" card, and confirmed the Approved regulatory-submission row showed an "Issue note" button. Filled in symbol `AMXSNI`→`AMXM5` and par value ₦1,000,000, submitted, and confirmed: the submission row now shows an "Issued" badge instead of the button, and the "Investment Notes (1)" card shows the note with total supply correctly computed as 800 (= ₦800,000,000 / ₦1,000,000). Queried the dedicated `GET /investment-notes/:id/metadata` endpoint directly and confirmed it returns exactly `{instrumentId: {admin, id: "AMXM5"}, meta: {"amanax.io/name": ..., "amanax.io/totalSupply": "800", ...}}` — the literal "discoverable via Token Metadata" gate requirement. Confirmed backend-level cross-role visibility (Fund Manager/sponsor, Trustee, SEC can all see the note; a `FundManager` role gets it via `GET /investment-notes`). Logged out, logged in as the SEC org through the actual login form, and confirmed its "Notes" nav item and new "Issued notes (1)" card render the same note correctly (symbol, total supply, approval reference) — no console errors, no failed network requests.

## How to run this locally
Same as [milestone-4.md](milestone-4.md) — all four services (`dpm sandbox`, `backend`, `agents`, `frontend`) need to be running. No new environment variables. Note: the dev sandbox was fully restarted mid-milestone (not just the backend/agents `tsx watch` processes) to pick up the new `InvestmentNote` template — the JSON Ledger API's `NO_TEMPLATES_FOR_PACKAGE_NAME_AND_QUALIFIED_NAME` error is the signal that a running sandbox is still serving a stale DAR and needs a real restart, not just a backend reconnect.
